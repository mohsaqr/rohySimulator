Cross-cutting conventions

These columns recur across many tables and carry platform-wide semantics (see CLAUDE.md):

Convention Column(s) Meaning
Soft-delete deleted_at Row is logically deleted when non-NULL. Most reads imply deleted_at IS NULL; physical purge is done by the retention sweep cron.
Tenant scoping tenant_id Multi-tenant isolation. Enforced by requireSameTenant() middleware, not ad-hoc WHERE clauses.
Audit / ownership created_by, created_at, updated_at Who authored the row and when; basis for ownership-based authz.
Snapshot binding *_snapshot Frozen copy taken at session start so later admin edits do not bleed into a live session.

Migration policy

Schema evolves only through versioned migrations/*.sql. Each migration is classified additive (previous-version code still runs) or destructive in migrations/MANIFEST.md, which bin/rohy-update reads to decide whether to auto-apply. Default is additive-only; destructive changes follow a multi-release dance.

0050_utc_iso_timestamps.sql additive One time contract across every log surface (RPS-1 §17). Two shapes had been accumulating in the same columns: anything a browser wrote arrived as 2026-08-29T12:34:56.789Z, anything falling through to sqlite's DEFAULT CURRENT_TIMESTAMP was written as 2026-08-29 12:34:56 — also UTC, but with a space, no zone marker and no milliseconds. sqlite's own date functions read the two identically (julianday(iso) - julianday(space) is exactly 0), so every julianday()/date() filter was always correct; two things were not. Ordering: these columns have TEXT storage, so ORDER BY <ts> is a string sort and ' ' (0x20) sorts before 'T' (0x54) — a row a full day later sorted first. Measured on the development database, 2169 of 3119 learning_events rows sat in the wrong position; after this migration, 0. Browser parsing: new Date('2026-08-29 12:34:56') is not an ISO string, so V8 parses it as LOCAL time and every server-stamped row rendered at the viewer's UTC offset — three hours out in Europe/Helsinki, different per viewer, different across a DST boundary. This migration rewrites the legacy shape in place across learning_events, interactions, login_logs, settings_logs, client_logs, llm_request_log, event_log, sessions, session_vitals, patient_record_events, investigation_orders, treatment_orders, alarm_events, scenario_events, emotion_logs, oyon_emotion_records, oyon_signal_windows, plugin_jobs and plugin_assets. Purely a reformat — strftime('%Y-%m-%dT%H:%M:%fZ', v) returns the same instant sqlite already read out of v, verified by SUM(julianday(timestamp)) being byte-identical before and after. Each statement is guarded twice: it skips rows already conforming (a GLOB) and rows sqlite cannot parse (the rewritten value IS NOT NULL), so an unexpected value is left alone rather than nulled. Duration columns (response_time_ms, time_elapsed) are deliberately untouched. Adds learning_events.client_time TEXT — the browser's own reading, kept beside the server's rather than instead of it, which turns clock skew from an invisible corruption into a measurable per-event quantity. system_audit_log is deliberately absent: its timestamp is inside the tamper-evident hash (canonicalRow() emits it as ts), so rewriting it would make all 509 historical rows fail verification — the chain cannot tell a reformat from a forgery, and that is the property it exists to have. It instead gains ts_utc, a VIRTUAL generated column over timestamp plus idx_system_audit_log_ts_utc(tenant_id, ts_utc DESC); a virtual column stores no bytes and is not one of canonicalRow's LOGICAL_FIELDS, verified by scripts/verify-audit-chain.js producing identical output with and without it. Order and date-filter that table by ts_utc, never by timestamp. Strictly additive: in-place value reformats, one nullable ADD COLUMN, one generated column, one index.
0051_utc_iso_domain_timestamps.sql additive Finishes what 0050 started, on the DOMAIN tables. 0050 fixed the log surface and, for the order tables, the rows that existed at that moment — but not their WRITERS, and it never touched users.last_login at all. Two live consequences. Last Active was wrong for everyone: users.last_login was written with CURRENT_TIMESTAMP, whose "YYYY-MM-DD HH:MM:SS" shape carries no zone marker although it is UTC, so Date.parse in usersUi.js read it as LOCAL and the Users tab was stale by exactly the viewer's UTC offset — reported from the field as "3 hours behind", and reproduced here at UTC+3 to the second. The order tables ended up holding both shapes at once, which is strictly worse than uniformly legacy: ORDER BY available_at is a string sort, so every legacy row sorts before every ISO row whatever the actual instants were, and OrdersDrawer's available_at + 'Z' — correct while all rows were legacy — produced ...ZZ and an Invalid Date for every row 0050 had normalised, breaking the worklist countdown on exactly the orders that predated the fix. This migration normalises users.last_login, users.locked_until, investigation_orders.{ordered_at,available_at,viewed_at} and treatment_orders.{ordered_at,administered_at,completed_at,discontinued_at}, and the writers are fixed in the same release (sqlNowPlus() in server/shared/time.js; every INSERT/UPDATE in auth-routes and orders-routes now names its time column). Same double guard as 0050 — a GLOB skips rows already conforming, so re-running is free, and strftime(...) IS NOT NULL leaves anything unparseable exactly as it is rather than nulling it. Purely a reformat: sqlite reads both shapes as the same instant, so julianday() over any of these columns is unchanged, and the SQL comparisons (datetime(io.available_at) <= datetime('now')) were always format-agnostic and stay correct. Soft-delete deleted_at columns are deliberately excluded — only ever tested IS NULL, never rendered or sorted.
0052_utc_iso_identity_timestamps.sql additive The last naive WRITERS on the identity and session tables (RPS-1 §17). 0050 normalised the log surface and 0051 the domain tables, but three writers kept re-arming the trap immediately afterwards. sessions.start_time: the session INSERT named no time column, so DEFAULT CURRENT_TIMESTAMP wrote the legacy naive shape back into a column 0050 had just normalised, and PUT /sessions/:id/end computed the stored duration with new Date(session.start_time) — which V8 parses as LOCAL time for that shape, so on a UTC+3 host a 15-second session was persisted as 3h00m15s and every debrief, cohort report and time-on-task figure downstream inherited the host's offset. users.created_at: five INSERTs (auth-routes register, users-routes create/batch/import, registration-routes approve) plus the first-boot seeder all omitted the column, so this table held 0051's conforming last_login beside a legacy created_at. oyon_settings.updated_at: written as a bare CURRENT_TIMESTAMP by PUT /addons/oyon/settings and returned to the admin UI as-is. All three writers are fixed in the same release (SQL_NOW from server/shared/time.js named explicitly on each INSERT/UPDATE, timeMs() for the duration arithmetic, and the session dedup window switched from datetime('now','-30 seconds') to sqlNowPlus() so its string comparison stays valid against an ISO column); this migration brings the stored rows in line, on sessions.{start_time,end_time,updated_at}, users.created_at and oyon_settings.{created_at,updated_at}. Same double guard as 0050/0051 — a GLOB skips rows already conforming so re-running is free, and strftime(...) IS NOT NULL leaves anything unparseable exactly as it is rather than nulling it. Purely a reformat: sqlite reads both shapes as the same instant, so every julianday()/date() comparison is unchanged. DELIBERATELY EXCLUDED: users.updated_at, because ~10 UPDATEs in users-routes still write it naively and converting the rows first would manufacture the mixed-shape column this migration exists to remove; sessions.duration, because it is a duration in seconds, not an instant, and the inflation in historical rows is unrecoverable after the fact (inventing a corrected number would be worse than a visibly wrong one — new sessions are correct from this release); system_audit_log.timestamp (hash chain, 0050's ts_utc still stands) and *.deleted_at (only ever tested IS NULL).
0053_interactions_source.sql additive Where a patient-conversation turn came from. interactions is the session's one patient thread and is now written from two surfaces — the chat room (typed / voice) and a plugin room such as the 3D bedside (room3d) — so without a marker the educator's transcript and every analytics query over interactions treat a spoken bedside question and a typed one as the same thing. One nullable ADD COLUMN source TEXT; rows written before this release read NULL ("unknown") rather than being relabelled, and pre-migration code never selects it. Validated on ingest to ^[a-z][a-z0-9_]{0,63}$, the plugin-id shape.
0054_patient_template_short_answers.sql additive The two default patient templates answer only what is asked: one question, one answer, one or two sentences, nothing volunteered.
